DSLs: Powerful but Inaccessible

✓ Domain-Specific Languages provide:

• Correctness guarantees
• Safety validation
• Formal verification
• Precise semantics

✗ BUT: They require specialized knowledge!

New users face a steep learning curve.
This limits adoption and creates friction.

Can We Talk to DSLs in Natural Language?

LLMs already claim to understand code...

"Generate SQL for top customers"
"Write Python to analyze this data"
"Create a regex for email validation"

But can we trust them with critical business logic?

What if we could combine LLM accessibility
with DSL reliability?

The Best of Both Worlds

Domain-Specific Languages (DSLs)

✓ Precise & Unambiguous
✓ Verifiably Correct
✓ Source of Truth for Business Logic

⚠ Barrier to Entry: 
Requires learning a specific syntax

Large Language Models (LLMs)

✓ Intuitive & Conversational
✓ Flexible Natural Language Input
✓ Accessible to Everyone

⚠ Barrier to Trust: 
Probabilistic and cannot guarantee correctness

Our Approach: Make DSLs Conversational

We enhance existing, reliable DSLs with a natural language interface.
The DSL remains the source of truth; the LLM acts only as a translator.

Architecture: The DSL as the Source of Truth

The framework is built on a set of formal artifacts that govern the system's behavior.

Key Artifacts:

  • Core DSL & Interpreter: The executable source of truth for all business logic and validation.
  • Schema: A "checklist" that defines the required data for each action, enabling guided conversations.
  • Linguistic Connector: A declarative mapping that bridges the formal DSL to natural language concepts.

Demo Part 1 (Depth): Handling Unstructured Input

The system can parse complex, real-world text and extract multiple, distinct DSL tasks.

Demo Part 2 (Intelligence): Guided Clarification

When a query is incomplete, the system uses the Schema to ask precise, helpful questions.

Demo Part 3 (Reliability): Enforcing Validation

The Core DSL & Interpreter act as the final gatekeeper, preventing invalid operations.

The Extensibility Promise: The Linguistic Connector

Adding a new DSL is primarily a configuration task, not a complex coding one.

The Process:

  • A Language Engineer defines the new domain's grammar, schema, and interpreter.
  • They then write a simple Linguistic Connector file (e.g., in YAML) to map the new DSL to language.
  • Our framework can even use a Template Generator to create a starter connector file automatically.

From Email to DSL. How?

Our system can extract multiple structured tasks from unstructured input:

📧 Unstructured Input (Email)

"Hi Team,

I wanted to let you know that we've secured
a new venue with four rooms:

Zimmer X1 – 10 seats, no AV facilities
Zimmer X2 – 40 seats, fully equipped with AV
Zimmer X3 – 20 seats, AV available
Zimmer X4 – 60 seats, AV and stage setup

This gives us a lot more flexibility for
planning events...

Best,
Sarah"

✨ Extracted DSL Instructions

System extracts 4 tasks:

1. create_venue "Zimmer X1" {
   capacity: 10, av: false }

2. create_venue "Zimmer X2" {
   capacity: 40, av: true }

3. create_venue "Zimmer X3" {
   capacity: 20, av: true }

4. create_venue "Zimmer X4" {
   capacity: 60, av: true,
   stage: true }

Each extracted instruction goes through the same validation and execution pipeline!

The System Blueprint & Flow

From unstructured input to validated execution

Processing Pipeline:

Unstructured Input: Email, document, or conversation

1. Conversation Layer:
   • Extracts ALL actionable tasks from input
   • Structures each task independently
   • Confirms batch with user if needed

2. Execution Layer (per task):
   • Converts each to formal DSL
   • Validates against business rules
   • Executes approved actions only

Conclusion & Contributions

Our Contribution

  • A framework to create reliable conversational interfaces for formal DSLs.
  • Decoupling of domain semantics (the DSL) from conversational mechanics (the LLM).
  • The concept of a "Linguistic Connector" to reduce manual prompt engineering and simplify extensibility.

Key Takeaway

This approach allows us to leverage the curated knowledge and reliability of DSLs while providing the accessibility of a modern, natural language interface.
