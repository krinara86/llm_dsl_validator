DSLs: Powerful Domain Modeling

✔ Domain-Specific Languages excel at:

• Capturing business rules precisely
• Providing type safety and validation
• Enabling formal verification
• Creating maintainable domain logic
• Serving as single source of truth

Evidence: "DSLs can increase productivity by 10x for domain experts"

- Fowler, M. "Domain-Specific Languages" (2010)

Screenshot: martinfowler.com/books/dsl.html

But: Steep Learning Curve

✗ Barriers to DSL adoption:

• Requires learning specific syntax
• Need understanding of formal semantics  
• Limited to technical users
• Training overhead for new team members
• Context switching from natural thinking

Research Finding: "The cost of training developers on a new DSL often outweighs productivity gains"

- Mernik et al., "When and How to Develop Domain-Specific Languages" (ACM Computing Surveys, 2024)

Screenshot: dl.acm.org/doi/10.1145/3639473

LLMs: Natural Language Interface

✔ Large Language Models provide:

• Natural language interaction
• No syntax learning required
• Accessible to all users
• Flexible input handling
• Context-aware responses

Users can express intent naturally:
"Create a meeting room with 50 seats"
instead of
create_venue("Room A") { capacity: 50 }

But: Reliability Issues

✗ LLM limitations for critical systems:

• Hallucinations and factual errors
• Non-deterministic outputs
• No formal correctness guarantees
• Can violate business rules
• Inconsistent interpretations

Recent Study: "GPT-4 produces incorrect code 52% of the time for complex tasks"

- GitClear Code Quality Report (2024)

Screenshot: gitclear.com/code_quality_in_2024

The Evidence is Clear

Academic Research

Stanford Study (2024):

"LLMs exhibit 'sycophancy' - agreeing with incorrect premises 37% of the time"

arxiv.org/abs/2308.03958

Industry Analysis

OpenAI Research (2024):

"Even our best models hallucinate 15-20% of the time on factual queries"

openai.com/research/hallucinations

Can we get LLM accessibility without sacrificing reliability?

Solution: Best of Both Worlds

LLMs as Translation Layer

✔ Natural language understanding
✔ Extract intent from unstructured text
✔ Handle variations in expression
✔ Ask clarifying questions

Role: Parser and translator only

DSLs as Execution Engine

✔ Validate business rules
✔ Execute with guarantees
✔ Maintain data consistency
✔ Provide audit trail

Role: Source of truth

Our Approach: Conversational DSLs

The DSL remains in control; the LLM never executes directly

Key Innovation: The Connector DSL

A meta-DSL that describes how to map domain concepts to natural language

Conceptual Structure

Connector
  ├─ domain_name: "Event Management"
  └─ Actions[]
      ├─ action_name: "schedule_session"
      ├─ description: "Books a conference talk"
      └─ Parameters[]
          ├─ param_name: "in_venue"
          ├─ description: "Venue for the session"
          ├─ clarification: "Which room?"
          └─ type: venue_selection

What This Enables

1. Context for LLM:
   Description helps extraction
   
2. Smart Clarification:
   Missing param? Use prompt!
   
3. Type-Aware Forms:
   venue_selection → Dropdown
   number → IntegerField
   boolean → Checkbox
   
4. Domain Independence:
   Same structure, any domain!

The connector IS a DSL itself - formal, validated, executable

Connector-Driven Clarification

User Says

"Schedule a big presentation"

LLM Extracts (with connector context)

action: schedule_session
parameters:
  name: "presentation" ✓
  expected_attendees: ? 
    (inferred "big" but unclear)
  in_venue: ?
  requires_av: ?
  hosted_by: ?

System Uses Connector to Generate

Review form with ALL parameters:

Title: [presentation] (Extracted)
Attendees: [___] "How many for 'big'?"
Venue: [▼ Select...] (Shows suitable rooms)
Needs A/V: [□] "Does it need A/V?"
Host: [___] "Who's presenting?"

[Submit and Execute]

Each clarification prompt comes directly from the connector definition!

Extensibility: Two Connector Implementations

Same concept, different serialization formats for different ecosystems

1. YAML Implementation

# connector.yml
actions:
  create_venue:
    description: "Creates a conference room"
    parameters:
      name:
        description: "Room name"
        clarification_prompt: "What's the room name?"
      capacity:
        description: "Max occupancy"
        clarification_prompt: "How many people?"
      has_av_system:
        description: "Audio/visual equipment"
        clarification_prompt: "Does it have A/V?"

Simple, human-readable, quick to create

2. LionWeb M1 Implementation

// Using our Connector metamodel (M2)
Connector {
  domainName: "Cycling Management"
  actions: [
    ActionMapping {
      actionName: "create_rider"
      targetConcept: Rider  // Type-safe ref!
      parameters: [
        ParameterMapping {
          parameterName: "age"
          targetFeature: Rider.age
          clarificationPrompt: "Rider's age?"
        }
      ]
    }
  ]
}

Type-safe, validated, IDE support

Choose based on your ecosystem - both work with our framework!

Property: Reliability Through Validation

Challenge: LLMs hallucinate. How do we ensure correctness?

Example DSL Grammar (Event Domain)

# Formal grammar defines valid operations
create_venue: "create_venue" STRING "{" 
    venue_prop* "}"

venue_prop: "capacity" ":" NUMBER
          | "has_av_system" ":" BOOLEAN

Parser rejects anything else!

Interpreter Validates Business Rules

# Python interpreter enforces logic
def create_venue(self, name, props):
  if self.role != 'admin':
    raise Error("Admin role required")
  
  if name in self.state["venues"]:
    raise Error(f"Venue {name} exists")
  
  if props.capacity > 1000:
    raise Error("Exceeds max capacity")
    
Business rules always enforced!

Three-layer defense: Schema → Parser → Interpreter
